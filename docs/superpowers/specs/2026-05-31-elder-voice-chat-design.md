# 老人端语音陪伴闭环设计

## 背景

当前项目已经完成云服务器部署基础，并已有 FastAPI、Next.js、PostgreSQL 仓储、聊天生成、豆包 TTS 和音色管理雏形。下一阶段先完善核心业务功能，优先交付老人端语音陪伴体验，再把它并入完整用户系统和云端数据闭环。

本设计只覆盖近期 B 阶段：老人端电话式语音对话。P4 稳定性与上线增强暂不作为主线，只保留不泄露密钥、不让页面崩溃、服务可启动等最低护栏。

## 目标

1. 老人端提供低认知负担的电话式语音陪伴界面。
2. 支持点击开始说话、点击结束发送。
3. 后端直接接入豆包 ASR，将老人语音识别为文字。
4. 通过 LLM 判断老人本轮想和哪个 AI 角色说话。
5. 复用现有聊天引擎生成共情回复。
6. 使用角色绑定音色或默认音色调用豆包 TTS。
7. 保存文字对话和 AI 回复音频，支持关闭通话后重播 AI 回复。

## 非目标

1. B 阶段不保存老人原始录音。
2. B 阶段不在老人端暴露角色切换、音色管理、历史筛选、设置等复杂入口。
3. B 阶段不优先做域名、HTTPS、日志告警、备份演练等上线运维增强。
4. B 阶段不做浏览器语音识别临时方案，直接以后端豆包 ASR 为准。

## 老人端体验

老人端第一版采用“老人友好型电话界面”，不是普通电话 App 复刻。核心原则是低认知负担、强状态反馈、少按钮、可取消、可重播。

页面结构：

1. 顶部显示当前扮演对象和状态提示，例如“正在和：女儿 小雨 说话”“可以开始说话啦”。
2. 中间放一个大号圆形主按钮，作为核心操作入口。
3. 底部只保留最近 2 到 3 条文字对话，每轮显示老人识别文本和 AI 回复文本。
4. AI 回复旁提供“重播”按钮，播放已保存的 AI 回复音频。
5. 辅助按钮按状态显示，避免常驻过多入口。

主状态流：

```text
开始说话 -> 正在听 -> 结束并发送 -> 正在理解 -> 正在回复 -> 播放中 -> 可以继续说话
```

辅助操作：

- 录音中：显示“取消本轮”。
- 录音结束后：显示“重新说 / 发送”。
- 播放中：显示“停止播放”。
- 播放结束后：显示“重播上一条”。

主按钮需要同时通过文字、颜色和动效表达状态，不能只依赖图标。

## 后端接口

新增聚合接口：

```text
POST /api/elder/voice-chat
```

前端提交字段：

```json
{
  "family_id": "xxx",
  "elder_id": "xxx",
  "persona_id": "",
  "voice_profile_id": "",
  "audio_data_base64": "...",
  "audio_format": "webm",
  "client_session_id": "optional"
}
```

其中 `persona_id` 和 `voice_profile_id` 可以为空。后端会根据 ASR 文本和 LLM 角色判断结果选择本轮角色与音色。`client_session_id` 用于连续对话归组。

后端处理流程：

1. 校验当前用户和家庭空间权限。
2. 调用豆包 ASR，把老人语音转成文字。
3. 如果识别为空或置信度过低，返回老人友好的“没听清”提示，不进入聊天生成。
4. 调用 LLM 判断本轮目标角色。
5. 根据目标角色找到绑定音色；如果没有绑定音色，使用默认豆包音色。
6. 调用现有聊天逻辑，复用家庭画像、记忆评分、陪伴策略和安全校验。
7. 调用豆包 TTS 生成 AI 回复音频。
8. 保存文字对话、命中角色、使用音色和 AI 回复音频路径。
9. 返回识别文本、AI 回复文本、可播放音频 URL 和状态信息。

响应示例：

```json
{
  "recognized_text": "小雨，我今天有点想你",
  "reply_text": "妈，我也想您。您慢慢说，我一直在呢。",
  "audio_url": "https://signed-url.example/audio.mp3",
  "session_id": "xxx",
  "message_id": "xxx",
  "matched_persona": {
    "persona_id": "xxx",
    "display_name": "女儿 小雨",
    "confidence": 0.86
  },
  "status": "ok",
  "debug": {}
}
```

## 智能切换角色

角色切换直接使用 LLM 判断，不采用规则优先方案。

输入给 LLM 的信息包括：

- ASR 识别出的老人文本。
- 当前家庭空间可用 AI 角色列表。
- 家人档案摘要。
- 默认陪伴角色。

LLM 返回结构：

```json
{
  "persona_id": "xxx",
  "matched_name": "小雨",
  "confidence": 0.86,
  "reason": "老人直接称呼了小雨"
}
```

如果置信度足够，使用该角色和绑定音色。如果置信度低、返回结果无效或目标角色不可用，则使用默认陪伴角色兜底。老人端只显示最终结果，不提供手动切换入口。

## 数据保存

B 阶段保存：

- ASR 识别文本。
- AI 回复文本。
- `family_id`。
- `elder_id`。
- 命中的 `persona_id`。
- 使用的 `voice_profile_id`。
- `asr_provider`。
- `tts_provider`。
- AI 回复音频路径。
- 创建时间。

B 阶段不保存：

- 老人原始录音。
- ASR 原始响应全文。
- TTS 原始响应全文。

AI 回复音频需要长期保存，用于关闭通话后重播。建议路径：

```text
generated-audio/{family_id}/{chat_session_id}/{message_id}.mp3
```

现有 `chat_sessions` 和 `chat_messages` 可以继续作为基础表。若字段不足，做最小迁移，避免引入复杂审计表。

## 错误降级

任何环节失败都不能让老人端页面崩溃。

- ASR 失败或识别为空：提示“刚才没听清，可以再说一遍吗？”
- 角色判断失败：使用默认陪伴角色。
- Chat 失败：提示“我这边有点卡住了，您稍等一下。”
- TTS 失败：保留文字回复，提示“语音暂时播放不了。”
- 音频保存失败：本轮可尝试即时播放返回音频，同时提示历史重播可能不可用。

错误信息面向老人要简短、温和，不展示 provider 错误、API Key、堆栈或内部字段。

## 阶段验收

1. 老人端能点击开始说话、点击结束发送。
2. 后端能调用豆包 ASR 得到识别文字。
3. 系统能通过 LLM 判断本轮想对谁说话，并选中对应 AI 角色。
4. 系统能生成 AI 回复，并用角色绑定音色或默认音色生成 TTS。
5. 前端能自动播放 AI 回复。
6. 最近对话展示 2 到 3 轮文字，并可重播 AI 回复音频。
7. 关闭页面后再进入，对话历史仍能看到文字并重播 AI 回复。
8. ASR、角色判断、聊天、TTS 任一环节失败时，页面不崩溃，有老人能理解的提示。

## 后续衔接

C 阶段再把语音体验并入完整云端闭环：

- 完善登录状态保持和 JWT 自动携带。
- 补齐用户、家庭空间、家庭成员数据隔离。
- 将档案、记忆、对话记录和角色音色绑定全部稳定落库。
- 增强对话历史按家庭成员、老人和时间查看。
- 将保存的文字对话用于长期记忆检索。
